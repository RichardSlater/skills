# github-supply-chain-hardening-remediation

## Purpose

This skill remediates an approved supply-chain hardening plan produced by `github-supply-chain-hardening-analysis`.

It:

- Takes one or more approved proposal JSON files and their target repositories.
- Clones each repository locally.
- Creates a remediation branch when file-based changes are needed.
- Applies file-based changes only.
- Runs relevant validation and tests.
- Commits the changes, signing the commit when local Git signing is available.
- Pushes the branch.
- Opens a GitHub pull request with validation evidence and manual follow-up items.

## When to use this skill

Use this skill when the user asks to:

- Execute an approved GitHub supply-chain hardening plan.
- Turn a generated hardening proposal into a branch and PR.
- Apply workflow, CODEOWNERS, documentation, dependency review, Scorecard, or other repository-file remediations.

Do **not** use this skill for initial organization/account analysis. Use `github-supply-chain-hardening-analysis` first.

## Inputs required

This skill requires:

- `repository_full_name`, for example `Scetrov/efctl`.
- `proposal_json_path`, generated by the analysis skill or otherwise approved by the user.
- Explicit user approval to push a branch and create a PR.

The user may supply multiple repository/proposal pairs for a batch remediation. Approval must clearly cover every repository in the batch and the creation of up to one PR per repository; approval for one repository must not be inferred to cover the others.

Optional inputs:

- `branch_name`, defaulting to `security/supply-chain-hardening-YYYYMMDD`.
- `base_branch`, defaulting to the repository default branch.
- `draft_pr`, defaulting to true unless the user asks for a ready-for-review PR.

## Token handling

The operator must not paste a token into chat.

Use local authentication from:

- `gh auth token` through the GitHub CLI.
- Existing `gh` CLI authentication for clone, push, and PR creation.
- `GITHUB_TOKEN` only if already present in the local environment and needed by a command.

Security requirements:

- Never print token values.
- Never write token values to disk.
- Never pass token values as command-line arguments.
- Never include token values in commit messages, PR bodies, logs, or generated files.
- Run leak checks on patches and PR body text before pushing/opening a PR.

## Remediation scope

This skill may apply file-based changes such as:

- `.github/workflows/*.yml` permission hardening.
- New dependency review workflow.
- New OpenSSF Scorecard workflow.
- New or updated OSV-Scanner workflow.
- `CODEOWNERS`.
- `SECURITY.md` or security documentation.
- `SECURITY-INSIGHTS.yml`.
- `docs/threat-model.md`.
- New or updated `.github/dependabot.yml` for version update configuration.
- Release provenance, SBOM, and artifact attestation workflow refinements.
- OpenVEX metadata files or directories for declared non-exploitable findings.

This skill must **not** directly mutate repository/org settings such as:

- Branch protection.
- Repository rulesets.
- Secret scanning settings.
- Push protection settings.
- Organization rulesets.
- Team permissions.

Settings remediations must be listed as manual follow-up items in the PR body.

## Best-practice `.github/dependabot.yml` template

When creating or updating `.github/dependabot.yml`, inspect the repository for every relevant dependency manifest and include one entry per ecosystem. Use the following best-practice defaults:

- **Schedule**: `weekly`.
- **Cooldown**: `5` days before a newly published version is proposed (`cooldown.default-days: 5`).
- **Groups**: batch low-risk **minor** and **patch** updates into a single grouped pull request, leaving major updates separate for explicit review.
- **Ecosystems**: cover the manifest/lockfile ecosystems that are actually present, such as `github-actions`, `npm`, `pip`, `gomod`, `cargo`, `maven`, `gradle`, `nuget`, `docker`, etc.

Template per detected ecosystem:

```yaml
  - package-ecosystem: <ecosystem>
    directory: <manifest-directory>
    schedule:
      interval: weekly
    open-pull-requests-limit: 10
    groups:
      low-risk:
        update-types:
          - minor
          - patch
    cooldown:
      default-days: 5
```

If the proposal identified specific ecosystems, generate a single `dependabot.yml` combining all detected entries. For example:

```yaml
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 10
    groups:
      low-risk:
        update-types:
          - minor
          - patch
    cooldown:
      default-days: 5

  - package-ecosystem: pip
    directory: /
    schedule:
      interval: weekly
    open-pull-requests-limit: 10
    groups:
      low-risk:
        update-types:
          - minor
          - patch
    cooldown:
      default-days: 5
```

Do not define ecosystems for manifests that do not exist in the target repository.

## Manual follow-up guidance

The agent must make the user's remaining responsibilities explicit. Do not merely say "configure repository settings". Include concrete UI/API steps, suggested values, and verification criteria.

After creating the PR, tell the user that file changes are only part of the hardening work. The user or a repository, organization or enterprise administrator must complete the settings tasks that cannot be safely changed by this skill.

### Branch protection or repository rulesets

Tell the user to review the repository default branch protection/ruleset configuration:

1. Open the repository on GitHub.
2. Go to **Settings → Rules → Rulesets** or **Settings → Branches → Branch protection rules**.
3. Create or update protection for the default branch, usually `main`.
4. Recommended controls:
   - Require pull requests before merging.
   - Require at least one approving review.
   - Require CODEOWNERS review after the PR adding `CODEOWNERS` is merged.
   - Dismiss stale approvals when new commits are pushed, where appropriate.
   - Require status checks before merge.
   - Require branches to be up to date before merge, where appropriate.
   - Restrict force pushes.
   - Restrict creation of matching branches to trusted maintainers/roles (rulesets: **Restrict creations**).
   - Restrict deletion of matching branches (rulesets: **Restrict deletions**; classic branch protection: uncheck **Allow deletions**).
   - Require signed commits or signed tags if compatible with the team's workflow.

Verification evidence to ask for:

- Screenshot or exported ruleset summary.
- List of required status checks.
- Confirmation that default branch direct pushes are blocked or restricted.

### Required status checks

Tell the user to add required checks only after the PR workflows have run at least once, because GitHub often requires checks to exist before selecting them.

Required checks must include the **specific job names** as they appear on pull request status lines. Common examples for repositories using the workflows added by this skill are:

- **CI/build/test job(s)** from `ci.yml`, `.github/workflows/test.yml`, or the repository's existing test workflow, for example:
  - `build`
  - `test`
  - `ci / test`
- **CodeQL analysis** from `codeql.yml` or GitHub's default CodeQL setup, for example:
  - `CodeQL`
  - `Analyze (language)` — for example `Analyze (python)`, `Analyze (javascript)`, `Analyze (go)`, `Analyze (rust)`.
- **Dependency review** from `dependency-review.yml`, typically:
  - `dependency-review`
  - `dependency-review / dependency-review`
- **OpenSSF Scorecard** from `scorecard.yml` if the team wants it blocking rather than advisory, typically:
  - `Scorecard supply-chain security`
  - `scorecard / analysis`
- **Release/provenance checks** only when relevant to release branches or tags, for example:
  - `provenance`
  - `release / attest`
  - `sbom`

Tell the user to match the exact job name shown in the PR **Checks** tab, including matrix job names such as `test (ubuntu-latest, 20)`.

Verification evidence to ask for:

- Names of checks configured as required, copied from the PR Checks tab.
- Screenshot or exported ruleset summary showing the required status checks list.
- Confirmation that a test PR cannot merge while required checks fail.

### Secret scanning and push protection

Tell the user to verify secret protection settings:

1. Open **Settings → Code security and analysis**.
2. Enable or verify:
   - Secret scanning.
   - Push protection.
   - Validity checks, where available.
   - Custom patterns for organization-specific credentials, if applicable.
3. If settings are managed by an organization or enterprise policy, ask the org admin to confirm inheritance.

Verification evidence to ask for:

- Confirmation that secret scanning is enabled.
- Confirmation that push protection is enabled.
- Any custom patterns added or explicitly deferred.

### Dependency graph, Dependabot alerts, malware detection, and code security alerts

Tell the user to verify the settings that GitHub manages in **Settings → Code security and analysis**:

1. Dependency graph must be enabled.
2. Dependabot alerts must be enabled.
3. Dependabot security updates should be enabled where supported.
4. Potential malware in open source dependencies (Malware detection) should be enabled where supported.
5. (Optional) Dependabot version updates are configured by the `.github/dependabot.yml` file included in the PR; confirm the file matches the repository's manifest ecosystems and schedule.
6. Code scanning alerts are visible and routed to maintainers.
7. Alert triage ownership is documented.

Verification evidence to ask for:

- Confirmation that dependency graph, Dependabot alerts, and Dependabot security updates are enabled in repository settings.
- Confirmation that potential malware in open source dependencies (Malware detection) is enabled.
- Confirmation that the `.github/dependabot.yml` file covers every dependency manifest/ecosystem used by the repository.
- Named owner/team for alert triage.

### CODEOWNERS rollout

If the PR adds or changes `CODEOWNERS`, tell the user:

1. Merge the PR adding `CODEOWNERS` first.
2. Then update branch protection/rulesets to require CODEOWNERS review.
3. Confirm all listed owners are valid GitHub users or teams with repository access.
4. Confirm sensitive paths are covered, especially:
   - `.github/workflows/`
   - dependency manifests and lockfiles
   - release scripts
   - infrastructure files
   - security documentation

Verification evidence to ask for:

- GitHub recognizes CODEOWNERS without errors.
- A test PR changing a protected path requests the expected owner review.

### AI and agentic workflow guardrails

Tell the user to document or configure governance for AI-assisted changes:

- AI-generated code must receive human review.
- Agents must not push directly to protected branches.
- Agent credentials must be least-privilege and revocable.
- Dependency changes generated by agents must pass dependency review.
- Security-sensitive generated changes must be reviewed by CODEOWNERS or maintainers.
- Agent runs must not execute untrusted code with privileged credentials.

Verification evidence to ask for:

- Repository or organization policy link.
- Confirmation branch protection prevents unreviewed agent mutation.
- Confirmation agent tokens are scoped to the minimum required repositories and permissions.

### Release and provenance follow-up

When the repository publishes releases, tell the user to verify:

- Release workflow permissions are scoped per job.
- Artifact attestations are generated for release artifacts using GitHub/Sigstore-backed attestation.
- SLSA Build Level 3 provenance is generated where possible, for example with `slsa-github-generator` or equivalent `attest` workflow steps.
- SBOMs are generated, attached, and ideally attested.
- Release artifacts and release metadata are signed with Sigstore/cosign or equivalent.
- Checksums/signatures are published.
- Tag creation and release publishing are restricted to trusted maintainers or environments.
- Environment approvals are used for sensitive publishing steps where appropriate.
- Immutable releases are enabled in **Settings → General → Releases** or at the organization level, so published releases and their associated tags cannot be altered.

Verification evidence to ask for:

- Link to a release showing checksums, signatures, SBOM, SLSA provenance files (for example `*.intoto.jsonl`), and/or attestations.
- Confirmation tag/release publishing is restricted.
- Screenshot or confirmation that release immutability is enabled.
- SLSA provenance verification command output (for example `slsa-verifier verify-artifact ...`).

## Execution flow

The agent must:

1. Read the proposal JSON.
2. Separate file-based changes from settings/manual changes.
3. Ask for explicit confirmation before any push or PR if the user has not already provided it.
4. Clone the repository into a temporary workspace using `gh repo clone`.
5. Inspect existing files before editing. Do not blindly apply proposal snippets if the repository already satisfies the control.
6. Determine whether the proposal contains at least one applicable file-based change. If every proposed file change is already satisfied, obsolete, or the proposal contains settings/manual changes only, treat the repository as a successful **no-op**:
   - Do not create a branch, commit, push, or PR.
   - Report why no file change was needed and retain any manual follow-up items.
   - If this is a batch, record the no-op result and continue with the next repository.
7. Create a new branch only when an applicable file-based change exists:

   ```bash
   git switch -c security/supply-chain-hardening-YYYYMMDD
   ```

8. Apply only changes that make sense against the current repository state.
9. Prefer precise, minimal changes.
10. Preserve existing pinned full-length GitHub Action SHAs.
11. For new GitHub Actions, pin to full-length commit SHAs and verify the SHA against the upstream tag with `git ls-remote`.
12. After editing, check `git status --porcelain`. If it is empty because the repository already contains the intended result, handle the repository as the no-op described in step 6 rather than attempting an empty commit.
13. Run validation appropriate to the repository, for example:

    ```bash
    git diff --check
    # YAML validation if workflows changed
    go test ./...        # for Go repositories
    npm test             # for Node repositories, when available
    cargo test           # for Rust repositories, when available
    ```

    If the analysis proposal included OpenSSF Scorecard results, re-run Scorecard after applying file-based changes to confirm score improvement:

    ```bash
    scorecard --repo github.com/owner/repository --format json --show-details > updated-scorecard.json
    ```

    Capture the updated overall score and any checks that moved from failing/low to passing. File-based changes can improve checks such as Token-Permissions, Pinned-Dependencies, Dangerous-Workflow, SAST, Security-Policy, Dependency-Update-Tool, CI-Tests, and Binary-Artifacts. Branch-Protection, Code-Review, Signed-Releases, and Vulnerabilities checks cannot be fully fixed by this skill and remain manual follow-up evidence.

14. Run leak checks before commit/push:

    ```bash
    git diff | grep -E '(gh[pousr]_|github_pat_|Authorization:|Bearer )'
    ```

    If any match appears, stop and investigate before proceeding.

15. Check whether local Git commit signing is available and use it when possible:

    ```bash
    git config --get commit.gpgsign
    git config --get user.signingkey
    git config --get gpg.format
    git config --get user.email
    git config --get user.name
    git commit -S -m "Harden supply-chain workflows and governance docs"
    ```

    Signing requirements:

    - Prefer signed commits for remediation PRs.
    - Use `git commit -S` when signing is configured and works locally.
    - Use a GitHub-verified commit email associated with the signing key; do not use placeholder identities such as `pi-remediation-test@example.invalid` for pushed remediation commits.
    - Verify the resulting commit locally with `git log -1 --show-signature`.
    - If GitHub shows the commit as unsigned or unverified, check whether the commit email is verified on GitHub and whether the GPG/SSH signing key is uploaded to the account.
    - If signing fails, stop and report the signing error unless the user explicitly approves an unsigned commit.
    - Do not disable signing to make progress without explicit user approval.
    - If the repository or organization requires signed commits, unsigned commits are not acceptable.

    Commit with a clear message, for example:

    ```text
    Harden supply-chain workflows and governance docs
    ```

16. Push the branch using `git push -u origin <branch>`.
17. Create a PR using `gh pr create`.
18. Report the PR URL, validation results, and manual follow-up items.

### Batch execution

When multiple approved repository/proposal pairs are supplied:

1. Process each pair independently in its own temporary workspace.
2. Classify each result as `pr-created`, `no-op`, or `failed`.
3. A `no-op` is a successful result, not a failure, and must never stop the batch.
4. A repository-specific failure stops work on that repository, but continue with the remaining approved pairs when it is safe to do so. Stop the entire batch only for a cross-cutting safety issue, such as leaked credentials or approval that does not cover the remaining repositories.
5. Finish with a summary for every repository, including the PR URL, no-op reason, or failure and required recovery action. Do not describe the overall batch as failed merely because one or more repositories were no-ops.

## Failure handling

Stop work on the current repository and report clearly if:

- The proposal JSON is missing or invalid.
- The proposal targets a different repository than requested.
- Clone fails.
- The remediation branch already exists and the user has not approved reuse.
- A proposed change is contradicted by the current repository state in a way that cannot be safely skipped.
- Validation/tests fail.
- Commit signing is available but fails.
- Leak checks detect token-like material.
- Push fails.
- PR creation fails.

An obsolete or already-satisfied change is not itself a failure. Skip that change; if no applicable file changes remain, classify the repository as a no-op. In a batch, follow the continuation and safety rules in **Batch execution**.

Do not force-push, delete branches, override repository settings, or open multiple PRs without explicit user approval covering every repository.
